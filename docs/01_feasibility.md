# ① 技術的実現可能性の評価（Feasibility Study）

## 結論（先に要点）

| 項目 | 評価 | 根拠 |
|---|---|---|
| 音楽のBPM・ビート検出 | **解決済み技術** | librosa / madmom / Beat This! で、ダンス系楽曲なら F値 90% 超。PoC でも合成ドラムを ±0.3% で推定 |
| GIF の動きの周期推定 | **現実的（想定より易しい）** | 「ループGIFは周期が T/n（整数分の1）に限られる」という制約で探索空間が離散化される。PoC の古典手法（オプティカルフロー＋循環自己相関）で合成 24 本中 24 本をオクターブ内で正解 |
| ビートへの同期再生 | **可能** | ブラウザで GIF をフレーム分解し Canvas に描画、AudioContext の時計で駆動。±15% の伸縮は知覚されにくい。PoC ページで動作確認済み |
| 多人数リアルタイム共有 | **可能（設計次第）** | フレームは送らず「イベント＋共有ビートグリッド」を送る。詳細は 03_architecture |
| 主リスク | 中 | (1) 実世界 GIF のうち周期性が明瞭なものの割合、(2) 低 fps GIF の位相精度、(3) 音楽・GIF の権利処理 |

## 1. 音楽のビート検出

### 手段の比較

| 手段 | 種別 | 精度（ダンス系） | 特徴 |
|---|---|---|---|
| librosa `beat_track` | Python / DSP | 良 | 導入最速。ハーフ/ダブルテンポ誤りあり。ダウンビート不可 |
| madmom (RNN+DBN) | Python / NN | 優 | 定番の高精度。ダウンビート可。近年メンテ停滞で numpy / Python 版の相性問題あり |
| Beat This! (ISMIR 2024) | Python / Transformer | 優 | 現時点で最高水準。ビート＋ダウンビート。GPU 推奨だが CPU でも可 |
| Essentia `RhythmExtractor2013` | C++ / Python | 良〜優 | 高速。`essentia.js` でブラウザ動作も可 |
| BeatNet | Python / NN | 良 | リアルタイム（ストリーミング）向け |
| web-audio-beat-detector / aubio.js | ブラウザ | 可〜良 | 端末内で完結。音源をサーバに上げなくてよい（権利・コスト面で重要） |

### 既知の限界と扱い
- **オクターブ誤り**（128 ⇔ 64 BPM）は本質的に曖昧。PoC でも 174 BPM を 87 と推定した。GIF 側も同じ曖昧さを持つため、**マッチングはオクターブ許容で設計する**（×½, ×2, ×4 を同一視）。
- ルバート・変拍子・テンポ変動は不得手。PoC では「ビート列の線形回帰残差」を `steadiness` として出し、低い曲は同期対象外にする。
- 小節頭（ダウンビート）が取れると「4 拍ループの GIF を小節に揃える」ことができ、体感が大きく向上する。Phase 2 で madmom または Beat This! を導入。

## 2. GIF の動きの周期性推定（本企画の核心）

### アプローチ比較

| # | 手法 | 長所 | 短所 | 計算コスト | 推奨用途 |
|---|---|---|---|---|---|
| A | フレーム差分 → FFT / 自己相関 | 最も単純。被写体を選ばない | カメラ揺れ・ディザ・背景に弱い。方向情報なし（位相が取りにくい） | 極小 | ベースライン、静止判定 |
| B | 密オプティカルフロー（DIS / Farneback）→ 符号付き速度・方向ヒストグラム flux | 方向あり → 「往復」と「方向転換の瞬間（視覚ビート）」が取れる。中央値フローでカメラ揺れ補正可 | 高速動作・低 fps でフローが破綻。全画面集計なので複数被写体に弱い | 小（160px で 1 遷移 数 ms） | **コア手法（PoC 実装済み）** |
| C | 姿勢推定（MediaPipe Pose / RTMPose / YOLO-pose） | 意味のある信号（腰の上下＝拍）。背景に無関係。ダンスの「ダウン」の位相が取れる | 人間のみ。アニメ・動物・低解像度・後ろ姿で失敗。動物用モデルは精度不安定 | 中〜大 | 人物 GIF の位相精緻化（補助） |
| D | 学習ベースの反復検出（RepNet / 時間自己相似行列 TSM） | クラス非依存。周期性の確信度が出る。非剛体でも可 | 64 フレーム前提の設計で短い GIF に不向き。要 GPU。独自データで微調整が必要 | 大 | Phase 2 以降、B で低信頼な GIF の救済 |
| E | 変化領域の重心（位置信号） | 極めて安価。フローが破綻する高速動作でも位置を追える | 複数被写体・カメラ揺れで無意味化 | 極小 | B の保険（PoC 実装済み） |

### 推奨: B + E をコア、C を人物用の補助、D を将来の救済策
理由:
1. GIF は短い（1〜4 秒）・低解像度・低 fps・ディザ入り。深層モデルが前提とする「きれいな動画」ではなく、古典手法の方が壊れにくい。
2. **ループ制約**が強力。継ぎ目なくループする GIF は、動きの周期が必ずループ長 T の整数分の 1（T/n）になる。候補が離散化されるので、循環自己相関を T/n の点だけで評価すればよい。
3. 視覚ビート＝「減速・方向転換の瞬間」という知見（Davis & Agrawala, *Visual Rhythm and Beat*, SIGGRAPH 2018）を、方向ヒストグラムの正の変化量（flux）で安価に実装できる。

### PoC 解析器の構成（`poc/gif_period.py`）
1. 全フレームを RGB 合成デコード。ディレイ ≤ 10ms は 100ms に正規化（ブラウザの実装に合わせる）
2. 長辺 160px に縮小、グレー化、ぼかし（ディザ除去）
3. 隣接フレーム間の DIS オプティカルフロー。末尾→先頭も計算し、ループの継ぎ目を判定
4. 中央値フローを引いてカメラ揺れを除去。速度 [px/s] に正規化して均一時間軸に再サンプル
5. 信号: 符号付き速度 vx/vy、変化領域の重心 cx/cy、平均速さ mag、方向ヒストグラム flux
6. 周期: 継ぎ目なし → 循環自己相関 R(T/n) の局所最大から最短の強い周期（最大値の 80% 以上）を採用。継ぎ目あり → 通常の自己相関
7. 位相: flux のピーク時刻＝視覚ビート。シーンカットは検出して無害化

### PoC の測定結果

合成 GIF（BPM 既知、20fps、24 本: バウンド／揺れ付きバウンド／ヘッドバング／振り子）

| 指標 | 結果 |
|---|---|
| 往復周期（native_bpm）がオクターブ内で正解 | 24 / 24 |
| 同・完全一致（±4%） | 17 / 24（外れ 7 本のうち 6 本は振り子。1 往復＝2 拍なので設計上オクターブ差） |
| 視覚ビート周期（impact_bpm）完全一致 | 20 / 24 |
| 非周期 GIF（ランダムウォーク）の棄却 | 正しくスコア 0 |
| 処理時間（CPU 1 コア、160px） | 0.1〜0.8 秒 / GIF |

実 GIF（GitHub 上で入手できたもの。GIPHY 等はこの環境からアクセス不可）

| GIF | 結果 | 評価 |
|---|---|---|
| ニュートンのゆりかご（0.82 s ループ） | 往復 73 BPM、衝突 146 BPM、スコア 0.96 | 物理的に正しい（1 往復に衝突 2 回） |
| 姿勢推定デモ（4 クリップ連結、6.6 s） | カット 3 箇所を検出 → 周期なし | 修正前はカット間隔 1.63 s を「周期」と誤認していた。カット検出が必須 |
| 5 fps のダンス動画（15 s） | 周期なし | 妥当。5 fps・寄せ集めでは拍が追えない |
| 静止に近い GIF | 静止判定 | 妥当 |

ダンス系の実 GIF での検証は未実施。**Phase 1 の最初の仕事は GIPHY / Tenor から 100 本集めて手ラベルすること**（02_poc_plan 参照）。

### 課題・エッジケースと対策

| 課題 | 影響 | 対策（PoC 実装済みは ✔） |
|---|---|---|
| 非周期的な動き（単発リアクション） | 同期不能 | ✔ 周期性スコアで棄却。「単発 GIF」としてドロップや小節頭に当てる別用途に回す |
| カメラワークの揺れ・パン | 全画面フローが汚れる | ✔ 中央値フロー減算。将来: 前景マスク、姿勢推定 |
| フレームレートのばらつき（フレームごとに異なるディレイ） | 時間軸が不均一 | ✔ 実時間軸に置いて均一再サンプル |
| ディレイの量子化（10ms 単位）・ブラウザの「≤10ms は 100ms」規則 | 意図と実再生速度がずれる | ✔ ブラウザと同じ規則で正規化。再生も自前制御なので齟齬なし |
| ディザ・パレット量子化ノイズ | 差分信号が汚れる | ✔ 縮小＋ぼかし。フローは差分より頑健 |
| シーンカット（複数クリップ連結） | 等間隔カットを周期と誤認 | ✔ 差分スパイクを検出して無害化、信頼度を下げる |
| ループ継ぎ目の有無 | 周期候補の離散化が使えるか決まる | ✔ 末尾→先頭の動き量で判定し、手法を切替 |
| 高速動作 × 低 fps でフロー破綻 | 速度信号が歪む | ✔ DIS フロー（大変位に強い）＋位置信号（重心）を併用 |
| 半拍／倍拍の曖昧さ（振り子は 1 往復 2 拍） | BPM が 2 倍ずれる | ✔ 往復周期と視覚ビート周期を両方出力し、マッチングでオクターブ許容 |
| 低 fps（10〜15fps）の位相精度 | ±1 フレーム = ±35〜50ms | 許容範囲内（音映像ズレの検知閾値: 音先行 約 45ms、音遅れ 約 125ms、ITU-R BT.1359）。将来はフロー補間で滑らかに伸縮 |
| 短い GIF（< 1 s、< 8 フレーム） | 周期の証拠不足 | ループ 1 周＝1 周期として扱い、信頼度を下げる（✔ ループ長プライア） |
| 長いループの「1 周期」 | ドリフトと区別不能 | ✔ ループが長いほど信頼度を下げる |
| 複数被写体が別リズム | 支配的な周期しか取れない | 将来: 空間分割（左右／グリッド）して個別解析 |
| GIF フォーマット自体（256 色・巨大・デコード負荷） | 配信コスト・端末負荷 | 取り込み時に WebM/MP4（＋タイミング JSON）へ変換して配信。解析は元 GIF で |
| 権利（音楽・GIF） | サービス化の前提 | 音源は端末内で解析し送信しない設計。GIF は GIPHY/Tenor API の規約（帰属表示等）に従う。詳細は 03/04 |

## 3. 同期再生の実現性（ブラウザ）

- `<img>` の GIF 再生は速度も位相も制御できない。**フレーム分解して Canvas に描く**のが唯一の現実解。
  - Chrome / Edge: `ImageDecoder`（WebCodecs）でネイティブにフレームとディレイが取れる（PoC で使用）。
  - Safari / Firefox: `gifuct-js` 等の JS デコーダで代替。または配信側で WebM/MP4 に変換し `requestVideoFrameCallback` で駆動。
- 時計は `AudioContext.currentTime` を唯一の基準にする。`Date.now()` や `setInterval` は使わない。
- 伸縮: 再生速度 rate = 周期 / (m × 拍間隔)。PoC 既定は ±15% まで許容（120 BPM の GIF を 128 BPM に合わせると +6.9%）。
- 位相: GIF 内の視覚ビート時刻 φ を拍に載せる。GIF 内時刻 g(τ) = (τ − 拍位相) × rate + φ（mod ループ長）。PoC ページで不変量を自動テスト済み。
- 目標精度: ±30ms（1 フレーム未満）。rAF は 60Hz なので描画自体は ±8ms。
