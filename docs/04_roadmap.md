# ④ 開発ロードマップ

## 全体像

| Phase | 期間（目安） | 問い | 出口（Go/No-Go） |
|---|---|---|---|
| 0. フィールテスト | Week 1 | 合わせると本当に盛り上がるか？ | 被験者の過半数が「同期あり」を選ぶ |
| 1. アルゴリズム検証 | Week 2〜5 | 実 GIF で自動推定できるか？ 何割使えるか？ | オクターブ内正解 ≥ 70%、使える GIF ≥ 40% |
| 2. プロトタイプ | Week 6〜12 | 一人で遊べる Web アプリとして成立するか？ | 外部 20 人が触って「また使いたい」≥ 50% |
| 3. Web サービス化 | Month 4〜6 | 多人数・リアルタイムで回るか？ 継続利用されるか？ | 週次アクティブ部屋数、同期精度 ±30ms、稼働率 |

## Phase 0: フィールテスト（Week 1）

目的: アルゴリズムを作る前に、コア体験の価値を確かめる。

タスク
- [ ] GIF 10 本を手で選び、ループあたりの拍数を目視で数える（`docs/02_poc_plan.md` Step 0）
- [ ] BPM 既知の曲 3〜4 曲を用意
- [ ] `poc/web/sync_player.html` で「同期／伸縮のみ／元速度」を比較
- [ ] 5 人に見せて感想と選好を記録

成果物: 選好の集計表、体感メモ（伸縮率の許容、半拍／倍拍の好み、位相ズレの気になり方）

判断: 否定的なら「同期」ではなく「テンポで選ぶだけ（伸縮なし）」に企画を縮小するか、中止。

## Phase 1: アルゴリズム検証（Week 2〜5）

目的: 実世界の GIF で周期・位相の推定精度と適用可能率を測り、解析器を確定する。

Week 2: データ
- [ ] GIPHY / Tenor API キー取得、クローラ（検索語 → 保存 → メタ CSV）
- [ ] 500 本取得（ダンス系 400、非周期 100）、pHash で重複排除
- [ ] 100 本を手ラベル（拍数、周期性、最初の「ダウン」フレーム、被写体種別）

Week 3: 評価と改善
- [ ] `poc/evaluate.py` で一括評価、失敗分類
- [ ] 改善の優先順位: シーンカット・前景マスク → 空間分割 → 姿勢推定（人物のみ）
- [ ] 位相誤差の測定（推定 impact と正解フレームの差）

Week 4: 音楽側と統合
- [ ] ビート検出の比較（librosa vs madmom vs Beat This!）を手持ちの 20 曲で。ダウンビートの要否を判断
- [ ] `match.py` の重み（伸縮許容、倍率の好み、小節ボーナス）を Phase 0 の体感メモで初期設定
- [ ] 曲 3 曲 × 500 本で自動マッチング → 上位 20 本 vs ランダム 20 本の体感評価（02 の Step 2）

Week 5: 確定
- [ ] 解析器 v1 を確定（`analyzer_version = 1`）、出力スキーマを固定
- [ ] 解析パイプラインをコンテナ化（Docker）、100 本/分の処理速度を確認
- [ ] 結果レポート（02 の計測テンプレート）

成果物: ラベル付きデータセット、解析器 v1、評価レポート、マッチング初期パラメータ

判断: オクターブ内正解 < 50% なら、自動推定を諦めて「人力ラベル ＋ 投票」中心の設計に切り替える（プロダクトとしては成立する）。

## Phase 2: プロトタイプ（Week 6〜12）

目的: 一人で遊べる Web アプリ。GIF ウォールが曲に合わせて踊る。

スコープ（入れる）
- 曲の入力: ローカル音楽ファイル（端末内でビート検出）＋ TAP テンポ
- 自動マッチング: 曲の BPM に合う GIF を 12〜20 本並べて同期再生（GIF ウォール）
- 検索語での絞り込み（"cat", "dance"）
- 投票ボタン（合ってる／ズレてる／半分／倍）
- 共有 URL（曲 BPM ＋ GIF セット。音源は共有しない）
- 1 万本規模の GIF プール（解析済み、WebM 変換済み、CDN 配信）

スコープ（入れない）
- 多人数リアルタイム、アカウント、Spotify 等の連携、モバイルアプリ

Week 6〜7: バックエンド
- [ ] FastAPI ＋ PostgreSQL、スキーマ（03 参照）、マッチング API（`tempo_class` インデックス）
- [ ] 取り込みパイプライン（クローラ → 解析 → 変換 → R2/S3）。1 万本投入
- [ ] 投票 API

Week 8〜10: フロントエンド
- [ ] Next.js、端末内ビート検出（essentia.js）＋ TAP、AudioContext 時計の同期エンジン（PoC ページの移植）
- [ ] GIF ウォール（Canvas → 負荷次第で WebGL）、小節頭での差し替え、位相合わせ
- [ ] 投票 UI、共有 URL、OGP

Week 11〜12: 仕上げと検証
- [ ] 同期精度の計測（描画時刻とビート時刻の差をクライアントから送信）
- [ ] 外部ユーザー 20 人にテスト、投票ログで解析器とマッチングを調整
- [ ] Vercel ＋ コンテナ（Fly.io / Cloud Run / Railway）にデプロイ

成果物: 公開デモ URL、投票データ、同期精度レポート

判断: 「また使いたい」< 30% なら、UX（見せ方・曲の入れ方）を見直してから Phase 3 に進む。

## Phase 3: Web サービス化（Month 4〜6）

目的: 多人数で同じ部屋に入り、同じビートで GIF を共有する「クラブハウス」。

Month 4: リアルタイム基盤
- [ ] 部屋モデル（共有ビートグリッド）、WebSocket ゲートウェイ、クロック同期（NTP 風）
- [ ] 小節頭スケジューリングでの一斉切替、ホスト権限（曲変更・GIF 投下）
- [ ] presence、リアクション（絵文字）、部屋のチャット（最小）
- [ ] 認証（ゲスト可）、レート制限

Month 5: コンテンツと品質
- [ ] GIF プールを 10 万本規模へ。高価パス（姿勢推定）を低信頼 GIF に適用
- [ ] 投票データで倍率・閾値を学習（まずはロジスティック回帰程度）
- [ ] ダウンビート推定を導入し、4 拍ループを小節に揃える
- [ ] フロー補間による滑らかな伸縮（低 fps GIF の位相精度向上）
- [ ] ユーザー投稿 GIF（規約、通報、モデレーション）

Month 6: 運用
- [ ] 監視（同期精度、切替遅延、エラー率）、アラート
- [ ] 負荷試験（部屋あたり 200 人、同時 50 部屋）。必要なら Ably 等へ移行
- [ ] コスト最適化（CDN キャッシュ率、変換品質）
- [ ] 収益・権利の整理（GIPHY/Tenor 規約、商用条件、音源の扱い）

成果物: 公開サービス、運用ダッシュボード、規約・ポリシー

## リスクと対策（横断）

| リスク | 兆候 | 対策 |
|---|---|---|
| 周期性のある GIF が少ない | Phase 1 の適用可能率 < 40% | 人力ラベル・投票で補完。単発 GIF を「ドロップ演出」に活用 |
| 半拍／倍拍の好みが割れる | 投票が分散 | ユーザーごとの好み設定、部屋単位の「ノリ」設定（ハーフタイム／ダブルタイム） |
| 端末間の同期ズレ | 計測で ±50ms 超 | クロック同期の頻度を上げる、描画を rVFC に、遅い端末は解像度を落とす |
| GIF 配信コスト | エグレス費が急増 | WebM 変換、CDN キャッシュ、サイズ上限 |
| 権利問題 | API 規約変更、音源の扱い | 端末内解析の原則を守る、規約のウォッチ、複数ソース（GIPHY・Tenor・ユーザー投稿） |
| Safari / Firefox 非対応 | `ImageDecoder` 不在 | 配信を WebM/MP4 に統一（Phase 2 で解決） |

## 未決事項（早めに決めたいこと）
1. **音源の主経路**: 各自のローカルファイル？ 同じ空間でのマイク入力？ ストリーミングサービス連携？（連携は API 制約が強く、Phase 3 以降が現実的）
2. **対象ユーザー**: パーティー／VJ 向けか、SNS 的に軽く遊ぶ層か。GIF ウォールの見せ方が変わる
3. **収益モデル**: 無料 ＋ プレミアム（部屋人数・自分の GIF）か、イベント向け B2B か
4. **プラットフォーム**: Web のみで進めてよいか（PWA で十分か）
